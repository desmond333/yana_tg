# AGENTS.md

Правила для AI-агентов и разработчиков, работающих с этим репозиторием.

## Язык

- Отвечать пользователю по-русски, если он явно не попросил другой язык.
- Не выдавать простыни англоязычного текста: документация и комментарии — по-русски.

## Принципы разработки

Пишем production-код, а не черновик. Перед любым изменением сверяемся с этим списком:

1. **Никакого «гавнокода».** Без временных костылей, закомментированных блоков, мёртвого кода и хаков поверх библиотек. Осознанное временное решение допустимо только с фиксацией в `../PLAN.md` и понятным сроком жизни.
2. **Никаких дубликатов.** Перед созданием компонента, функции, типа или константы — поиск по `shared/ui`, `shared/lib`, `shared/config` и соседним слайсам. Похожее расширяем или обобщаем, а не копируем.
3. **Переиспользование по умолчанию.** Повторяющийся UI-паттерн становится компонентом дизайн-системы, повторяющаяся логика — утилитой или хуком в подходящем слое. Третий повтор одного и того же — сигнал к обобщению.
4. **Думаем о будущем.** API слайсов, типы и данные проектируем так, чтобы переход на внешний API, ru → en и рост контента не требовали переписывания UI. Решение оцениваем на «завтра», а не только на «сегодня».
5. **Всё по FSD.** Слои, слайсы, сегменты и публичные API соблюдаются без исключений; обход правил «ради скорости» запрещён. Если правило реально мешает — обсуждаем и меняем само правило, а не нарушаем молча.
6. **Минимальный diff.** Не переписываем соседний код без необходимости и не трогаем чужие слайсы «заодно». Каждое изменение — точечное и объяснимое.

## Коммиты

Соблюдаем Conventional Commits: `<type>[область]: <описание>`.

- type — обязателен, строчными буквами: `feat`, `fix`, `refactor`, `docs`, `style`, `test`, `perf`, `build`, `ci`, `chore`, `revert`.
- Описание — настоящее время, императив: `add feature`, не `added feature`.
- Коммит делается только когда пользователь явно попросил, одним логическим изменением.

## Архитектура: Feature-Sliced Design 2.1

Слои и порядок импортов — только сверху вниз:
`src/app` → `src/pages` → `src/widgets` → `src/features` → `src/entities` → `src/shared`.
Импорт вверх (нижний слой тянет верхний) запрещён.

Обязательные правила:

1. **Слайсы и сегменты**: каждый слой состоит из слайсов (`entities/product`, `features/lang-switcher`); слайс — из сегментов `ui/`, `model/`, `api/`, `lib/`, `config/`.
2. **Публичный API**: только `index.ts` слайса, с явными именованными экспортами. Глубокие импорты во внутренности чужого слайса и wildcard-реэкспорты (`export * from`) запрещены.
3. **Изоляция слоя**: слайсы одного слоя не импортируют друг друга (`features → features`, `entities → entities` запрещены). Общий код опускается ниже — в `entities` или `shared`.
4. **Локальность импортов**: cross-слайсовые импорты — через alias `@/...`; импорты внутри своего слайса — относительные (`./`, `../`).
5. **`shared` без бизнес-логики**: `shared/ui` — презентационные компоненты, `shared/api` — API-клиенты, `shared/lib` — чистые утилиты, `shared/config` — константы, `shared/i18n` — словари. Верхние слои он не импортирует. Импорт из `shared` — только через публичный API сегмента (`@/shared/lib`).
6. **Тонкие страницы**: `pages` — композиторы виджетов и фич. Подсистемы, модалки и панели живут в `features/*` или `widgets/*`, а не в папке страницы.
7. **Никаких legacy-каталогов**: `src/store`, `src/services`, `src/lib`, `src/data`, `src/hooks`, `src/components`, `src/utils` запрещены. Любой новый файл создаётся сразу в канонической структуре.
8. **Границы проверяются автоматически**: ESLint (`boundaries`), Steiger, `scripts/check-structure.mjs`, Husky pre-commit. Обход правила = красный `npm run check`.

Новый слайс создаётся генератором: `npm run gen:slice <layer> <slice-name>`. После изменений архитектуры обновляйте `PROJECT_MAP.md`.

## Комментарии в коде

Любые комментарии в коде (JSDoc, инлайн, пояснения к секциям, комментарии в CSS/HTML/TSX) запрещены, пока пользователь явно не попросил. В diff не должно попадать ни одного комментария.

## Чистый код

Строго запрещены вложенные тернарные операторы (`a ? b : c ? d : e`). Вместо них: словари-константы `Record<Key, Value>`, функции с ранним `return`, `switch`, обычные `if / else`. Простые одноуровневые тернарники разрешены.

## Библиотеки вместо самописного кода

Для крупных или нетривиальных фич (редакторы, графики, виртуализация, работа с датами, аудио, сложные манипуляции) сначала предлагаются 1–2 зрелые проверенные библиотеки с лицензией и весом бандла. Решение принимается после согласования с пользователем.

## Дизайн-система и витрина

Если в проект добавляется UI-кит, действуют правила:

1. Интерактивные компоненты строятся на готовых headless-примитивах (например, Radix UI), а не с нуля.
2. Дублирование компонентов и разрозненная инлайн-разметка запрещены — сначала проверь `src/shared/ui`.
3. Каждый компонент дизайн-системы обязан быть представлен в DEV-витрине (`/dev/components`): все состояния, варианты, темы.
4. Стилизация — только через токены проекта: Tailwind-классы (`bg-panel`, `text-muted`, `border-line`, `rounded-lg`) или CSS-переменные (`var(--bg)`) там, где классы не подходят.

## Документация

`README.md` обновляется при добавлении новых технологий, инструментов и архитектурных решений. `PROJECT_MAP.md` — карта кодовой базы: структура, слайсы, текущее состояние. Обе карты должны быть актуальны после каждого изменения кода.
